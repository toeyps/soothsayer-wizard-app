# Wizard — Design System

**Owner:** `ui-design-lead` (Fable). Other agents read this file and follow it; they propose changes to the lead instead of editing it.
**Status:** v1, written 2026-10-04 from the design session that produced the current mockups (see `APP_MAP.md`). Real token values live in `src/App.css` `:root` — when this file and `App.css` disagree, `App.css` is what ships; fix whichever is wrong and note it here.

---

## 1. Who the app is for, and the feeling we want

- **Users:** reliability / maintenance engineers in Thai power and process plants. They know their machines and tags; they are not data scientists. They work for long sessions on large desktop screens, often comparing many sensors at once.
- **Job of the app:** historical (offline) sensor CSV → explore → group failure modes → train models on normal operation → set health-score points → export model files.
- **What Wizard does (corrected by the user 2026-10-07):** it **analyses offline data** and **finds abnormal machine behaviour**. A model learns what normal operation looks like; the health score (0–100) says how far each period in the data strays from that normal. It does **not** predict, forecast or warn ahead of a failure — with offline data that is impossible, and no model type with that concept exists yet.
- **Feeling:** a precise instrument, calm and dark, with one moment of "wow" per screen (the welcome machine, the glowing chart). Never playful, never cluttered. Data first; chrome recedes.
- **The product promise the visuals must tell:** *learned normal, and where the data strays from it* — a reading drifting away from its band and turning amber ("abnormal", score below 80) is the recurring visual story (welcome callouts, health score, alarm bars). The story is read from history, never shown as a live warning. Copy rule in §5.

## 2. Two layers of the visual language

### 3.2 Typography
- **Inter** for UI text; **JetBrains Mono** (`--mono`) for tags, numbers, units, dates, code-like values.
- Scale used in the app: 10.5 (meta, uppercase labels with +0.06–0.14em tracking) · 11.5–12 (secondary) · 12.5–13 (body) · 14–15 (panel titles, 600) · 20–28 (page titles, 650–700, tracking −0.02 to −0.025em) · welcome hero only `clamp(36px, 3.4vw, 44px)` (700, −0.035em; was a fixed 46 — clamped 2026-10-08 so the headline stays two lines below ~1,220 px).
- Big numeric readouts: mono 18–24, weight 600, tracking −0.03em, coloured by the series.
- **⚠️ Installed app renders in the fallback fonts, not Inter / JetBrains Mono (found by dev 2026-10-08, shipped in 0.9.0).** The production CSP in `tauri.conf.json` blocks Google Fonts, so the installer falls back to **Segoe UI** (UI text) and **Consolas** (`--mono`) on Windows. `npm run dev` still loads the web fonts, so the dev window lies about what the user sees. Consequences and rules:
  - Design and check every text-fitting decision with the fallbacks: label widths, chip and pill widths, mono column alignment, the welcome callout card (its `LABEL_W` had to go 204 → 224 because Segoe UI / Consolas run wider than Inter / JetBrains Mono). Mockups should switch to `Segoe UI`/`Consolas` for a final width check before hand-off, and any width constant in code gets a test measured with the fallback fonts.
  - Keep `font-family` stacks explicit: `Inter, "Segoe UI", system-ui, sans-serif` and `"JetBrains Mono", Consolas, ui-monospace, monospace`, so the fallback is the one we designed for and not whatever the WebView picks.
  - **Open decision for the user (not taken yet):** (a) **bundle Inter + JetBrains Mono locally** in the app (`@font-face` from the Vite bundle — self-hosted assets need no CSP change) so the installed app matches the design; or (b) **accept Segoe UI / Consolas** as the shipped typography and retune the scale in this section for them. Widening the CSP to allow Google Fonts is *not* an option on the table (CLAUDE.md: never widen the CSP without explicit approval, and a network font would also break the offline promise in §1). Lead's suggested default: (a).

### 3.3 Space, radius, elevation
- Spacing steps: 4 · 6 · 8 · 10 · 12 · 14 · 16 · 20 · 24 px. Panels pad 12–16; window gutters 12.
- Radius: 5–7 (chips, small buttons) · 8–10 (inputs, buttons) · 11–14 (cards, rows) · 16 (Studio cards, modals).
- Elevation: base cards have no shadow; Studio cards, popovers and modals do. Modals sit on a 55% black scrim with **2 px** blur (`App.css` `.bmw-modal-backdrop` and the shared modal scrim — corrected 2026-10-09 from "3 px"; the multi sensor picker uses the same 2 px).

### 3.4 Motion
- Hover/selection transitions 150 ms. Chart redraws are instant (no tweening data).
- One ambient animation per screen at most (welcome machine). Always honour `prefers-reduced-motion` (render a still frame).

## 4. Patterns (reuse these, don't invent parallels)

- **Sensor label — ONE standard (2026-10-08, customer item 3; reference https://claude.ai/artifact/FvViQRhtz8RiXxE2YwhT6o §1):** two variants of the same component (`SensorLabel`), nothing else.
  - **Stacked** (lists, cards, headers, picker rows with room): line 1 = description (sans 12.5, weight 500, `--text-primary`) + unit chip (`.unit-badge`, mono 10); line 2 = tag (mono 10.5, `--text-faint`).
  - **Inline** (one line: picker triggers and rows, chips, condition rows, chart subtitles, toasts, tooltips): description then tag in faint mono, **no brackets**. The description ellipsises; the tag has `flex-shrink: 0`. Unit appears inline only next to a value ("68.41 DEGC"), never inside the label.
  - **Order is always description first, tag second.** Never tag-only when a description exists; never "(tag)" first.
  - **No description:** the tag takes line 1 in mono at the same weight and colour; no second line and no "no description" placeholder (lesson 1).
  - **Component:** a group header (two-letter badge + name + selected/total) wherever a list is grouped; never repeated per row. Outside a grouped list (condition row, Workbench detail header) it is a small outlined chip after the tag.
  - **Chart axes only** (pair-plot cell headers and row labels, under ~120 px): tag alone in mono 10 with a dotted underline; hover/focus shows the stacked label + unit + component (`AxisLabel`). Scatter axis titles have room and use Inline.
  - **Tooltips and value boxes** (line chart, scatter, tag points): inline label left, value + unit in mono right, coloured by the series.
  - **Truncation:** every truncating label carries `title` = "DESCRIPTION · TAG · UNIT · Component". **Search** everywhere matches description, tag, unit and component. Description case is kept as the tag-name file gives it. Special sensors use the same label with the ƒ / Σ badge before the description.
  - **Shipped 2026-10-09 (commit ce23c64, local):** `src/components/sensor/SensorLabel.tsx` (+ `sensorInfo.ts` for metadata through React context) is in every window. **Scope exception, now the standard:** the **Tag names table** on Step 2 (Add sensor data) keeps its own column layout — it *is* the mapping the label reads from, so showing the label there would be circular. Everything else uses `SensorLabel`.
- **Per-sensor actions live on the sensor row in the right panel** (user, 2026-10-04: the side placement is easier than the instrument cards): 🔔 alarm setpoints (popover with LL/L/H/HH ticks; active levels show as small chips under the name) and 📁 add-to-failure-group (opens the assignment sheet), visible on hover and always on selected rows; FG chips under the name. Instrument cards keep only view controls (colour, show/hide, pin Y, remove) — never duplicate an action in two places.
- **Sensor picking — ONE picker (2026-10-08; reference §2–3 of the same artifact):** `SensorPicker` (today `SensorPickerModal`), search + collapsible component groups (collapsed; a search opens every matching group), rows in the Inline label + unit chip. The Dashboard right panel stays the place to explore.
  - **Single** (one value: Highlights "Colour by", Filter rows, Running condition rows, Y / X / criteria sensor, the Fit chart's X selector, Scatter X / Y): the trigger looks like a select (inline label + chevron; a compact 24 px form for chart toolbars); it opens an **anchored popover under the control**; one click picks and closes; **no OK button**.
  - **Multi** (a set: predictor sensors, special-sensor sources): selected values as chips with a remove ×, an "Add…" dashed button opens a **modal** with checkboxes; nothing changes until OK; Cancel / Escape / scrim discard.
  - **Native `<select>` and `SensorAutocomplete` are retired for sensors.** This includes the Scatter X / Y selects that were left native on 2026-09-22: that decision assumed a centred modal; an anchored popover costs the same two clicks as a select, so the objection no longer holds.
  - Required-and-empty = dashed amber trigger; disabled = 50 % with the reason as placeholder. Keyboard: Space/↓ opens into the search box, ↑↓ move, →← open/close a group, Enter picks/toggles, Esc closes and returns focus to the trigger (Esc closes only the picker, never the modal behind it).
  - **Shipped 2026-10-09 (commit ce23c64, `src/components/sensor/SensorPicker.tsx`; `SensorAutocomplete` and `SensorPickerModal` are deleted). Dev's deviations, recorded here as the standard:**
    - A single picker that has no room below **opens upward with a fixed height** (`pickerMaxHeight()`, `reserveHeight`) and grows up into that space — the search box never moves while the list shrinks on typing or grows on opening a group. The popover **never goes under the 32 px titlebar**.
    - The multi picker's scrim blur is **2 px**, the same as every other modal (§3.3), not 3 px.
    - Opening a single picker **expands the current value's group**; when the workspace has **≤ 10 sensors every group starts open** (nothing to collapse at that size). The "everything collapsed, search opens matching groups" rule above applies from 11 sensors.
    - Focus moves into the search box only after the popover is positioned (`preventScroll`), so the page never jumps.
- **Colour picking — ONE picker (2026-10-08, customer item 4; reference §4):** `ColourPicker`, used for sensor line colours, time highlights, value-highlight ranges and pair-plot clusters. The **swatch is the button** (16 px, radius 4, 1 px border; no pipette icon, no round swatch). It opens an anchored popover: 12 palette swatches in the §4 chart order (6 × 2), a **check** on the current colour, a small **dot** on colours another item on the same chart already uses, then "Custom colour" which unfolds the HSV square + hue slider (today's `ColorPlatePicker`) and a mono hex field. Picks apply immediately; Esc closes and returns focus. Keyboard: arrows move across the grid, Enter/Space picks, Tab reaches Custom and the hex field. Never `<input type="color">` (the OS dialog is unthemed and cannot mark colours in use). Default colours for new items keep their existing per-feature cycle; only the picker is shared.
  - **Shipped 2026-10-09 (commit ce23c64, `src/components/sensor/ColourPicker.tsx`).** Recorded as the standard: the palette is the **same 12 colours** as `LINE_CHART_COLORS` and the **default line colour order is unchanged** (amber stays in slot 4 — colours in existing workspaces must not change; the "align the array to the §4 order" note of 2026-10-08 is withdrawn). The 16 px swatch sits in a 24 px hit area; the current colour is ringed with `box-shadow` (outline stays for `:focus-visible`); the hex field accepts Shift+Tab back into the grid.
- **Component groups:** coloured two-letter badge + name + "selected / total".
- **Model kinds:** I / R / C badges (18 px rounded square, kind colour on 16–30% tint). UI says **"Relation model"** — the algorithm name is confidential.
- **Status:** a pill (Complete / Trained / Incomplete / Set points needed / Fix set point) + a corner dot on kind badges (amber = needs input or re-train, red = fix, green = complete). One rule feeds all of them (`modelSetPointFlag`).
- **Failure-group assignment:** the matrix sheet (rows = groups, columns = I/R/C toggle cells, search, All/Assigned, ‹ › to step sensors, create group inline). Removing a model's last group deletes that model — say so in a toast.
- **Confirmations:** inline in the row (rename, delete) rather than OS dialogs, except irreversible bulk deletes.
- **Blocked actions:** keep the button visible but disabled, with the reason as text next to it (footer) and a tooltip. Exactly one blocked primary action per page (e.g. Mark complete).
- **Validation:** required-empty = dashed amber field + "Required"; invalid = red field; a "Checks" list explains every issue with its fix. Equal values count as invalid when a strict order is required.
- **Charts:** the chart the user is already reading is where they set values (lines on the chart, draggable later). Result charts go **below** the inputs that drive them (users read top-to-bottom as cause → effect). Score/health colours: ≥80 green, below 80 amber→red.
- **Multi-sensor line charts (colour + layout rules, 2026-10-04):**
  - Palette = the shipped `LINE_CHART_COLORS` hues, ordered for maximum difference first: `#3b82f6` blue, `#10b981` emerald, `#f43f5e` rose, `#8b5cf6` violet, `#06b6d4` cyan, `#84cc16` lime, `#d946ef` fuchsia, `#f97316` orange, then amber/teal/indigo/pink. Amber/red are kept late because they mean alarms. A sensor keeps its colour slot for the window's lifetime; the colour picker marks colours already on the chart.
  - **Overlay** (default): one grid, one Y-axis per sensor alternating left/right, axis line + ticks + a unit chip in the sensor's colour; lines 1.3 px, no glow. **Focus**: hovering a legend chip, an instrument card or an axis brightens that sensor (2.1 px, glow, soft fill) and dims the rest to ~16%.
  - **Split**: one lane per visible sensor sharing the time axis; lane = colour stripe + name/unit chip + own min/max; best for 4+ sensors. Hover crosshair runs through all lanes with a value badge per lane.
  - No legend row above the chart (removed 2026-10-04): show/hide lives on the instrument cards below (eye) with "Show all on chart" on that tab; hovering a card focuses its line.
  - Highlights by time: *Band* (tinted window) or *Recolour line* (segments inside the window take the highlight colour). By value (Scatter only): points coloured by one sensor's value bands, grey outside.
  - Alarm setpoints: four levels LL/L/H/HH, user ticks which to draw; L/H amber long-dash, LL/HH red short-dash, label at the right end.
  - Tag point: pinned markers in their own colours with a value box per sensor and Δ vs the first tag.
- **Train / Test periods (model validation, 2026-10-07 — extends the CURRENT Build Model Workbench, not the Studio redesign):** colours `--train` = accent blue `oklch(.68 .17 245)`, `--test` = magenta `oklch(.74 .16 340)` (not a kind, category or state colour). Known problem = test colour with a 135° hatch; event = danger dashed vertical line labelled EVENT. Dashboard highlights are NOT drawn on Workbench charts (they only feed "From Highlights" and the amber train-overlap warning).
  - **Time scopes on charts (revised 2026-10-09, see "Build Model Workbench pages" below):** every Workbench time chart names its scopes in a thin **strip above the plot** — train labels on the upper lane, scoring labels on the lower lane, plain coloured mono text, no pills inside the plot. Inside the plot a scope is only a faint fill (train blue 6 %, scoring magenta 5 % with a dashed outline, Known problem a light hatch); rows outside every period are left out (the line breaks — a gap), so the chart shows exactly what was scored. Reference lines (±1SD, ±3SD, ±2RMSE, 80) are labelled **outside the plot on its right edge**; the user's own set points (L / H, the 80 / 0 residuals) are the strongest lines and carry their value inside the plot at the right end — **in the shortest exact form of the typed value** (set points are stored as numbers, so "4.60" shows as `H 4.6`; `H 85`, `L 40.5`, `+12.25`; never padded, never rounded). Rust's validation messages quote them the same way. The same rule holds for validation messages and Checks lines that quote a set point ("H must be above +3SD (79.35)" quotes the typed `85`, the computed `79.35` through `fmtNum`). Only computed values (±1SD, ±3SD, ±2RMSE, axis ticks) go through `fmtNum` (§4 "Numbers").
  - **Information-only results (revised 2026-10-09 — just-score rule, see "Scoring periods" under "Build Model Workbench pages"):** scoring results never block anything and are **never judged**: every result tile is neutral (numbers only: `% of running time below 80`, lowest score). The 2026-10-07 green/amber verdicts (false-alarm share for Normal, lead time / "Not detected" for Known problem) are withdrawn with the labels.
  - **"Lowest" rule:** "below 80" means below 80 for 1 h of running time (a constant beside the data minimum).
  - **Coverage strips** (modal + Step-1 card) show test periods too, in the test colour (Known problem hatched), captioned like "117 d train · 42 d test".
  - **Data amount: no hard minimum (user, 2026-10-07 — blocking would stop them training with little data).** Below the recommended amount (`RECOMMENDED_TRAIN_DAYS` = 30 days of train running time) an amber warning only; Train is blocked only by the technical errors Rust already raises (e.g. `NO_DATA`). Never disable an action on a day count.
  - **Test scoring failure notice** (`.vt-fail`) is amber, never red — the train side still shows. Codes: `test_scoring_failed` (only this one offers "Try again"), `test_scoring_outdated`, `test_scoring_too_large` (no retry, no "try again" wording).
  - **Numbering:** test results keep the number of their position in the test list (`T1`, `T2` …), even when an invalid period in between is skipped.
  - Rules: a train period is required to Train (the Step-1 "No train period" chip is amber); a test period is required before Mark complete; a test period MAY overlap a train period (user, 2026-10-07 — e.g. train Jan–Mar, test Jan–Dec; results use the whole test period and the row carries a neutral note "includes N d of train data"); no train period blocks Apply too (no test period only gets an amber note); a train period overlapping a highlight is amber only; changing only test periods re-scores (no re-train) but needs Mark complete again.
- **Welcome machine art (shipped 2026-10-08 in 0.9.0, commit 062e24d; SPEC `docs/design/handoff/welcome-c6-orbit/README.md`):** the one ambient animation of the welcome screen, cycling the user's six machine types (lesson 8).
  - **C6 dot art:** about 6,000 dots on the hero (`HERO_PARTICLES = 6000`), 2,400 on the SetupRail mini (`MINI_PARTICLES = 2400`), **edge-weighted** (rims, seams, box edges and bolt rings get most of the dots), drawn by a **single pixel-buffer renderer** (dots add light into one `ImageData`, one `putImageData` + one `drawImage` with `lighter` per frame; buffer pixel ratio capped at 1.25, stepped down on a 260k-pixel budget). Group colours `GROUP_ARR`: blue, violet, orange (the §3.1 exception), white. Timing HOLD 4.6 s / TRANS 1.8 s. The mini has no labels, no grid, no drag, dot alphas × 0.6.
  - **Orbit drag, hero only — "feels like a 3D model viewer":** press-and-drag with pointer capture (mouse, touch, pen); cursor `grab` / `grabbing`; turn is unlimited left/right, tilt clamped −10°…+80° (default 18°); auto-spin and the machine cycle pause while held and resume 1.5 s after the glide ends; on release the turn glides to a stop in about 0.5 s (capped at 12 rad/s, no glide after an 80 ms hold) and the **tilt eases back to the default over about 2 s**, keeping the turn angle; double-click resets by the nearest route. **No zoom** (user decision). No visible "Drag to turn" chip — the canvas carries `aria-label="Drag to turn the view."`. Callouts stay visible while dragging and follow the rotated anchors.
  - **Callout:** label reads `● ABNORMAL` (amber `--warn`, drift threshold > 12 %). The callout card is **224 px wide** (`LABEL_W`), a width that must be sized and tested with the real fallback fonts (§3.2) — at 204 px the label overlapped "Exhaust gas temperature" in the installed app. Sparkline sits at `b.x + 114`, width 80; leader offsets ±70 px, leader ends on the nearest card edge. "Illustration · simulated readings" uses `--text-secondary`.
  - **Reduced motion:** a still frame — no auto-spin, cycle or glide; drag still works and redraws only while dragging. The still frame shows the trending sensor already in the `● ABNORMAL` state, so the image still tells the §1 story.
- **Empty/locked states:** a dashed box the same size as the content it replaces, with one sentence saying what unlocks it.
- **Numbers:** tabular mono; units always shown; thousands separators for counts.
  - **Number formatter — two rules, not one (shipped 2026-10-09, commit ce23c64; `src/components/sensor/sensorInfo.ts:147-194`). Replaces the SPEC's "one formatter, 3 decimals":** the code review found typed thresholds being rounded in chips (`> 0.0005` showed as `> 0.001` — a wrong statement of the training condition).
    - **Values the user TYPED keep every typed decimal** — `fmtNumText` (text, e.g. a condition's or filter's value) / `fmtNumExact` (a typed value already parsed, e.g. a highlight range's min/max). Thousands separators only; `1.50` stays `1.50`, `0.0005` stays `0.0005`. Chips, condition rows, Step-1 summaries and highlight labels that echo an input use these.
    - **COMPUTED values use `fmtNum`** (tooltips, the tag-point box, stats, readouts): en-US, separators, up to 3 decimals (`fixed3` pads to 3 where a column must line up) — and **never shows a non-zero value as 0**: below 0.001 → 3 significant digits (`0.00012`); ≥ 1e9 → whole numbers with separators; ≥ 1e15 → scientific (`1.235e+15`). Null/NaN → `–`.
    - Never format a value inside an `<input>` or a CSV export. The Workbench's own `chartTheme.ts` formatter is unchanged (its charts are computed-only).

- **Group settings by kind, in one place each (user, 2026-10-04: "setting ของแต่ละประเภทมันควรอยู่ที่เดียวกัน")** — Dashboard map: *chart view* (Overlay/Split, Tag point, Line/Scatter/Pair; Scatter's X, Y and **Colour by + value bands**) = the bar above the chart · *time* (navigator, dates, First/Last N, aggregation, reset) = under the chart · *per-sensor display* (colour, show/hide, pin Y, remove) = instrument cards · *per-sensor data settings* (alarm setpoints, failure groups) = the sensor rows on the right · *filters* and *time highlights* = their tabs under the chart · *navigation* (Build Model) = the header only. Never split one kind of setting across two places.

### 4.1 Flow patterns from the customer requirement set (2026-10-08, items 5 / 6 / 8+9 — designs, not yet in code)

- **Failure groups come first (setup step 3).** After "Add sensor data" the setup rail gets **Step 3 — Failure groups** (rail: Name the project · Add sensor data · Failure groups · Explore in Dashboard). The step *names* the failure modes only: a quick-add input (Enter adds a group and keeps focus, so several can be typed in a row) above one card per group with Name (inline, required, duplicate = red + message) and always-visible single-line Description and Recommendation fields that grow. Sensors are **not** assigned here — that needs the chart, so it stays in the Dashboard (📁 on the sensor row → assignment sheet). The step is skippable ("Skip for now" as a text link, never a primary button); after Continue/Skip the Dashboard lands on the **Failure Groups tab** with a blue callout ("Your failure groups are ready. Next, assign the sensors…" / "No failure groups yet. Failure groups come first…") and an "Assign sensors →" link on every empty group. A reopened project with zero groups lands the same way. ## 5. Content rules
- English UI copy; replies to the user in Thai.
- Say what the user recognises (Tag names, On the chart) rather than system terms (mapping, selected sensors) — but don't rename shipped labels without the user's OK.
- Buttons say exactly what happens ("Mark complete", "Open Dashboard", "Create sensor"). Errors say what is wrong and how to fix it, no apologies.
- Simulated/illustrative data is labelled as such ("Illustration · simulated readings").
- **No forecasting words in user-facing copy:** never "predict", "before it happens", "early warning", "forecast", "ahead of time", "about to fail". Say what the app does: *find abnormal behaviour*, *learn normal operation*, *score how far a period strays from normal*, *in historical / offline data*. ("Predicted" is fine only where it names the Relation model's fitted value — actual vs predicted at the same time — not a future.) Internal code names such as `predictiveModel` are unaffected.

## 6. Lessons from user feedback (do not repeat these mistakes)
1. Show only what exists — no placeholder slots for missing things.
2. Don't leave demo toggles, alternative concepts or extra items in a mockup the user has already decided on ("เดี๋ยวงงตอน implement"). Remove the losers once a choice is made.
3. Don't add items the user didn't list (e.g. extra machines). Ask or offer instead.
4. One place to set a value; one page per job; the whole model flow lives in the Build Model Workbench (no "full view").
5. Keep left/right columns balanced in height; avoid dead space under a short chart.
6. Results below inputs, not above.
7. Hidden tabs hide important charts — if a chart is essential (Relation model fit), show it.
8. Machine graphics must not lock the app to one machine type — the welcome art cycles the user's six machine types.
9. Lead with the user's real data/terms (real tags, units, FG names) in mockups.
10. Don't promise prediction or forecasting; Wizard analyses offline data and finds abnormal behaviour against learned normal (user, 2026-10-07: the welcome hero "See the failure before it happens" promised something the product cannot do). Check every headline, kicker, subtitle, window description and illustration label against §5.
11. **A mockup starts from the CURRENT real code (user correction, 2026-10-12 — standing rule for every design run):** the working tree, plus the newest dev handover entries (`docs/handover/`). It may differ from the real app **only in the change being proposed** — never an older harness, never a stale copy of a page dev has since changed. The agent's report **proves it with a `git diff --stat`** (the mockup copy against the working tree) and **lists every intentional difference in plain words**; the SPEC FINAL is written from that list only. A difference that is not on the list is a bug in the mockup, not a design decision.

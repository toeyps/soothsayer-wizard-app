# กติกาการเขียน Manual Test Plan — ผู้ทดสอบคือ BA ไม่ใช่ developer

ใช้ทุกครั้งที่เพิ่ม / แก้ข้อใน `docs/testing/MANUAL_TEST_PLAN.md` (ทั้งแผนถูกเขียนใหม่ตามกติกานี้เมื่อ 2026-10-22 ตามที่ผู้ใช้ขอ: "คนที่ทำหน้าที่เทสคือ BA ไม่ใช่ dev") · หลังแก้ให้รัน `python scripts/build-manual-test-html.py`

## ผู้อ่านคือใคร
- BA ที่รู้เรื่องงาน (เครื่องจักร, sensor, ค่าที่วัด, การเสียของเครื่อง) ใช้ Windows / Excel / Notepad / File Explorer เป็น
- **ไม่รู้โค้ด** ไม่รู้ศัพท์ developer และไม่รู้ว่าข้างในโปรแกรมทำงานอย่างไร
- ต้องอ่านแล้ว **ทำตามได้ทันที** และ **ตัดสินได้ทันทีว่าผ่านหรือไม่ผ่าน** โดยไม่ต้องถามใคร

## สิ่งที่ต้องคงไว้เหมือนเดิมทุกตัวอักษร (ห้ามแก้)
1. บรรทัด `## KEY` (เช่น `## BMW`) — คงไว้ตรงตำแหน่งเดิม
2. **id ของทุกข้อ** (`BMW-12`, `WFA-3`, `IMP-88b` …) ลำดับเดิม จำนวนเดิม — ห้ามเพิ่ม ห้ามลบ ห้ามรวมข้อ ห้ามแยกข้อ
3. เครื่องหมายท้ายหัวข้อ `🆕` / `👀` / `🐍` — คงตามเดิม (ข้อไหนไม่มีก็ไม่ต้องใส่)
4. ข้อความบนหน้าจอที่อยู่ในเครื่องหมายคำพูด (ชื่อปุ่ม เมนู ข้อความเตือน ภาษาอังกฤษ) เช่น `"Mark complete"`, `"Export failed · nothing was written"` — ผู้ทดสอบต้องเอาไปเทียบกับจอ **คงคำเดิมตรงตัว**
5. ชื่อไฟล์ / โฟลเดอร์ที่ผู้ทดสอบต้องเปิดหรือใช้ (`C:\TSdata`, `EXP-data.csv`, `%APPDATA%\com.prompt-solution.tauri-app`), คำสั่งที่ต้องรัน (`python scripts/...`), tag ของ sensor ในข้อมูลทดสอบ (`TEMP/1`, `BRG_TEMP`), ตัวเลข วันที่ จำนวนแถว
6. HTML comment บรรทัดเดี่ยว เช่น `<!-- ── Training data: Custom ── -->` — คงไว้ที่เดิม
7. ความหมายของการทดสอบ: **ทุกขั้นตอนและทุกสิ่งที่ต้องตรวจในข้อเดิมต้องยังอยู่** (ห้ามตัดสิ่งที่ต้องตรวจทิ้ง ห้ามแต่งพฤติกรรมใหม่ที่ไม่มีในข้อเดิม) — แค่ **เขียนให้เข้าใจง่าย**

## รูปแบบไฟล์ (โปรแกรมสร้างหน้าเว็บอ่านตามนี้ — ผิดรูปแบบ = ข้อนั้นหาย)
```
## KEY

### ชื่อหมวด (ภาษาคน)

_คำอธิบายหมวด 1 บรรทัด (ถ้าเดิมมี)_

- [ ] **ID — ชื่อข้อ: ทดสอบอะไร เป็นประโยคสั้น** 🆕
  - ขั้นตอนที่ 1
  - ขั้นตอนที่ 2
  - **คาดหวัง:** สิ่งที่ต้องเห็น
```
- หัวข้อทั้งบรรทัดต้องอยู่ในรูป `- [ ] **ID — ชื่อ**` ตามด้วยช่องว่าง + เครื่องหมาย (ถ้ามี) — ห้ามมี `**` อื่นในชื่อข้อ
- ขั้นตอน: บรรทัดละ 1 ขั้น ขึ้นต้นด้วย 2 ช่องว่าง + `- `
- **ทุกข้อมีบรรทัด `  - **คาดหวัง:** ` บรรทัดเดียว และเป็นบรรทัดสุดท้ายของข้อ** ต้องอยู่บรรทัดเดียว (ห้ามขึ้นบรรทัดใหม่) — ถ้ามีหลายเรื่องให้คั่นด้วย ` · ` หรือใส่เลข (1) (2) (3)
- ระหว่างข้อเว้น 1 บรรทัดว่าง · ท้ายหมวดคงบรรทัด `---` ตามเดิม (ถ้า input มี)

## วิธีเขียนให้ BA อ่านง่าย
1. **ขั้นตอน = สิ่งที่มือทำ ทีละอย่าง ตามลำดับ** — บอกว่ากดอะไร ที่ไหน (ชื่อปุ่มตามจอ) · ถ้าเดิมมีหลายการกระทำต่อกันด้วย `→` ในบรรทัดเดียวยาว ๆ ให้แยกเป็นหลายบรรทัด
2. **คาดหวัง = สิ่งที่ตาเห็นบนจอ / ในไฟล์** — เขียนเป็นสิ่งที่ตรวจได้ (ข้อความอะไรขึ้น ปุ่มกดได้หรือไม่ ค่าเป็นเท่าไร) ไม่ใช่เหตุผลข้างในโปรแกรม
3. **ตัดศัพท์ dev ทิ้ง หรือแปลเป็นภาษาคน** — ตัวอย่างคำที่ต้องเลี่ยง: autosave mirror, race, debounce, cache, fingerprint, atomic, staging, IPC, broadcast, event, state, payload, round-trip, regex, sanitize, escape, null, array, field, key (ของ JSON), parse/parser, backend/frontend, Rust, TS, Python sidecar, sequence counter, re-render, flush, dry run, ISO 8601, offset, UTF-8 BOM, epoch, stale, workspace id, schema
   - ถ้าเรื่องนั้นสำคัญต่อการตรวจ ให้อธิบายด้วยผลที่เห็น เช่น:
     - "การบันทึกอัตโนมัติของ Dashboard ไม่เขียนทับ" → "ค่าที่เพิ่งแก้ยังอยู่ ไม่ย้อนกลับเป็นค่าเก่า"
     - "dry run" → "แอปลองตรวจก่อนว่าจะเขียนไฟล์อะไรบ้าง"
     - "`null`" → "ค่าว่างที่เขียนว่า null"
     - "offset +07:00" → "ท้ายเวลามี +07:00 (หมายถึงเวลาไทย)"
     - "ISO" → "รูปแบบวันเวลาแบบ 2025-01-31T13:05:00"
     - "UTF-8 ไม่มี BOM" → "ไฟล์ภาษาไทยที่ Excel บางเครื่องอาจเปิดแล้วเห็นเป็นตัวอักษรแปลก ๆ"
     - "Python sidecar" (🐍) → "ส่วนคำนวณ Relation model ที่ติดมากับตัวติดตั้ง"
   - **ตัดทิ้ง**: ชื่อฟังก์ชัน ชื่อไฟล์โค้ด (`.ts`, `.tsx`, `.rs`, `.py` ยกเว้นสคริปต์ที่ผู้ทดสอบต้องรัน), ชื่อตัวแปร (`runningConditionMode`, `healthExport` …), เหตุผลทางเทคนิคว่าทำไมโปรแกรมทำแบบนี้, คำว่า "(แทน BMW-25)" / "(id เดิม)" / ประวัติการแก้ของข้อ
4. ศัพท์ของแอปเองที่จำเป็น (sensor, tag, Failure group, Model, Train, Health score, Set point, Running condition, Mark complete, Export results, Dashboard, Workbench, Special sensor, Clustering, Relation model, Individual) **ใช้ได้** — มีหน้าคำศัพท์อธิบายไว้แล้ว ไม่ต้องอธิบายซ้ำทุกข้อ
5. ข้อที่ขึ้นต้นว่า "⚠ สงสัยว่ายังไม่ผ่าน" / "สงสัยว่าเป็นบั๊ก" → เขียนเป็น "⚠ ข้อนี้อาจยังไม่ผ่าน — ให้บันทึกผลตามที่เห็นจริง" แล้วตามด้วยสิ่งที่ควรเป็น
6. ข้อที่ต้องเปิดไฟล์ในเครื่อง (log, JSON, CSV) → บอกวิธีเปิดสั้น ๆ (เช่น "กด Win+R พิมพ์ ... แล้ว Enter", "คลิกขวา → Open with → Notepad")
7. ภาษาไทยสุภาพ ประโยคสั้น ไม่ต้องยาวกว่าเดิมมากเกินจำเป็น — อ่านแล้วต้องรู้เลยว่าทำอะไรและดูอะไร

## 2. งานที่เหมาะกับ BA/SA ในโปรเจกต์นี้ (เรียงตามลำดับแนะนำ)

### งานที่ 0 — ทดสอบ regression ของงานที่เพิ่งทำเสร็จ (2026-09-09) ก่อนงานอื่น

**ทำไมต้องอยู่ก่อนงานที่ 1:** วันนี้มีการแก้ไข "Manage Special Sensors" และ "Build Model — Overview" หลายจุดพร้อมกัน (5 commit ในวันเดียว) ยังไม่มีใครทดสอบบนแอปจริง (ติดตั้งจาก installer) เลยสักครั้ง — commit local ไว้หมดแล้วแต่ **ยังไม่ push** เพราะรอทดสอบยืนยันก่อน นี่คืองานที่ให้ผลตอบแทนสูงสุดตอนนี้ เพราะเป็นจุดเดียวที่บล็อกการ push จริง

เปิดแอปที่ build ไว้ (หรือขอให้ dev build installer ใหม่ให้) แล้วไล่ทำตามนี้:

**A) Rename special sensor** (หน้า Add Special Sensor → แท็บ Manage → กด ✏️ ที่แถวไหนก็ได้)
1. เปลี่ยนชื่อ (field NAME) ของ special sensor ตัวหนึ่งที่ **มี** sensor อื่นสร้างต่อจากมัน (เช่นมี B = A + 1) แล้วกด Save changes — เช็คว่า B ยังคำนวณค่าถูกต้องอยู่ไหม (ไม่ใช่ค่าว่าง/error) และในกราฟที่ plot ทั้ง A(ชื่อใหม่) กับ B อยู่ ค่ายังต่อเนื่องไม่กระโดด
2. ลองเปลี่ยนชื่อเป็นชื่อที่ซ้ำกับ sensor ตัวอื่นที่มีอยู่แล้ว (ทั้งชื่อ raw sensor จาก CSV และชื่อ special sensor อื่น) — ต้องขึ้น error และกด Save ไม่ได้
3. ลองลบชื่อออกให้ว่าง — ต้องขึ้น "Name is required" และกด Save ไม่ได้
4. ปิดแอปแล้วเปิดใหม่ (หรือเปลี่ยน workspace ไปมา) — เช็คว่าชื่อใหม่ยังอยู่ ไม่กลับไปเป็นชื่อเดิม และสีเส้น/แกน Y ที่ pin ไว้/alarm line ที่เปิดไว้/Failure Group ที่ผูกไว้ ยังคงอยู่ครบตามชื่อใหม่

**B) บังคับกรอกครบ 4 ช่อง** (Name/Description/Unit/Component)
1. หน้า Create: ลองสร้าง special sensor ใหม่ กรอกแค่บางช่อง — ปุ่ม "Add sensor" ต้องกดไม่ได้ (จาง) จนกว่าจะกรอกครบทั้ง 4 ช่อง พร้อมข้อความบอกว่าขาดช่องไหน
2. หน้า Manage → เปิดแก้ไข: ลองลบ Component ให้ว่าง — ปุ่ม "Save changes" ต้องจางลงและกดไม่ได้ (ก่อนหน้านี้เคยปล่อยให้ว่างได้แล้ว fallback เป็น "Uncategorized" เงียบ ๆ — ตอนนี้ต้องพิมพ์เองแล้ว)

**C) หน้า Build Model — Overview**
1. กดปุ่ม "Group by Model Type" มุมขวาบน — ต้องเห็น section แยกตาม Individual / Relationship / Clustering (ตัวไหนไม่มีโมเดลจะไม่มี section ว่าง ๆ โผล่มา)
2. เปิดโมเดลที่ยังไม่ครบข้อมูล (เช่น Relationship ที่ยังไม่เลือก predictor) — ปุ่ม "Build Model →" ต้องอยู่ต่อจาก "Save changes" ที่มุมล่างขวาของฟอร์ม (ไม่ใช่บนหัวแถวเหมือนก่อน) และต้อง**จางลงกดไม่ได้**เหมือนปุ่ม Save changes เป๊ะ ๆ — ถ้ายังดูสีเข้มกดได้เหมือนปกติ นี่คือบั๊กที่เพิ่งแก้ไปแล้วแต่ยังไม่ยืนยันบนแอปจริง
3. กรอกข้อมูลให้ครบ แล้วลองกด "Build Model →" — ต้องพาไปหน้า train ได้ปกติ และค่าที่เพิ่งกรอกต้องถูกบันทึกไว้ด้วย (ลองกลับมาเช็คฟอร์มอีกทีว่าค่ายังอยู่)

**ถ้าพบปัญหาข้อไหน:** จดขั้นตอนทำซ้ำให้ละเอียดแบบเดียวกับ template ในหัวข้อ 4 ด้านล่าง แล้วส่งกลับมาทันที — ก่อนจะไปทำงานที่ 1 ต่อ

**สืบเนื่อง:** [`docs/MANUAL_TEST_PLAN.md`](MANUAL_TEST_PLAN.md) / [`docs/manual-test-plan.html`](manual-test-plan.html) เขียนไว้ก่อนงานวันนี้ ยังไม่ได้ปรับให้ตรงกับ UI ใหม่ (ช่อง Name แก้ไขได้แล้ว, มีเครื่องหมาย * ที่ทุกช่อง, ปุ่ม Build Model ย้ายตำแหน่ง, มีตัวเลือก Group by Model Type) — ถ้าทดสอบแล้วผ่านหมด งานถัดไปที่ทำได้เลยคือช่วยชี้ให้ dev รู้ว่าข้อไหนใน test plan เดิมพูดถึง UI ที่เปลี่ยนไปแล้วบ้าง

## 3. งานที่ 2 แบบละเอียด — วิเคราะห์รายงาน 5 ข้อใน Notion

### เป้าหมาย

**ไม่ใช่การแก้บั๊ก** — เป้าหมายคือเปลี่ยนจาก *"มีคนบ่นมา 1 บรรทัด"* ให้เป็น **spec ที่ dev หยิบไปทำต่อได้ทันทีโดยไม่ต้องถามอะไรซ้ำ**

รายงานดิบใน Notion ตอนนี้มีแค่ประโยคเดียว ไม่มี: ทำซ้ำยังไง / severity แค่ไหน / กระทบใครบ้าง / พฤติกรรมที่ถูกต้องควรเป็นยังไง — พอไม่มีสิ่งเหล่านี้ dev จะเสียเวลาไปกับการหาให้เจอก่อน มากกว่าการแก้จริง งาน BA คือไปตัดขั้นตอนนั้นออก

### ขั้นตอนทำงาน (ทำแบบนี้กับทุกข้อ)

1. **อ่านรายงานดิบ** ใน Notion — บางทีมีบริบทเพิ่มที่ไม่ได้ก็อปมาลง BACKLOG.md
2. **ลองทำซ้ำในแอปจริง** (ติดตั้งจาก installer ไม่ใช่ dev mode) — จดขั้นตอนที่ทำให้ละเอียดที่สุด แบบเดียวกับที่เขียนใน MANUAL_TEST_PLAN.md
3. **ถ้าทำซ้ำได้** → หาว่าพฤติกรรมที่ถูกต้องควรเป็นยังไง (บางทีต้องถามผู้ดูแลโปรเจกต์หรือผู้ใช้จริงว่า "ที่ถูกคืออะไร")
4. **ถ้าทำซ้ำไม่ได้** → บันทึกไว้ว่าลองแล้วไม่เจอ พร้อม environment/ข้อมูลที่ใช้ลอง เผื่อเป็น edge case เฉพาะชุดข้อมูล
5. **เขียนเป็น spec สั้น ๆ** ตาม template ในหัวข้อ 4
6. ส่งกลับมาให้ dev หยิบไปทำ

ไม่จำเป็นต้องอ่านโค้ดเป็น แต่ถ้าอ่านได้แม้แค่ระดับ "หาไฟล์ที่เกี่ยวข้อง" จะช่วยให้ spec แม่นขึ้นมาก — ด้านล่างนี้เป็นสิ่งที่สืบไว้ให้แล้วคร่าว ๆ ทั้ง 5 ข้อ เพื่อให้เห็นตัวอย่างว่าการวิเคราะห์ระดับนี้ให้ผลลัพธ์อะไร ใช้เป็นจุดเริ่มต้นได้เลย ไม่ต้องเริ่มจากศูนย์

### ① "FG page back to dashboard → ACTUAL: back to start program"

**สิ่งที่เจอในโค้ด:** ทั้งแอปมีปุ่ม "กลับ" อยู่จุดเดียวคือลูกศรซ้ายมุมบนของแผงกราฟ (`Dashboard.tsx` บรรทัด ~1716) และมันเรียก `handleBackToImport` เสมอ — พากลับไปหน้า Import (จุดเริ่มโปรแกรม) ไม่ว่าผู้ใช้จะอยู่แท็บ Sensor หรือแท็บ Failure Groups ก็ตาม เพราะแท็บ Failure Groups ไม่ใช่หน้าแยก มันคือแค่แท็บย่อยในแผงขวาของ Dashboard เดียวกัน

**สมมติฐาน:** ผู้ใช้ที่อยู่แท็บ Failure Groups กดลูกศรนี้โดยคาดว่าจะ "กลับไปแท็บ Sensor" (อยู่ในบริบทเดียวกัน) แต่ดันหลุดออกจาก workspace ไปเลย — เป็นปัญหาการตีความไอคอนผิดจุดประสงค์ ไม่ใช่บั๊กทางเทคนิค

**สิ่งที่ต้องทำต่อ:** ยืนยันกับผู้ใช้จริงว่าสถานการณ์ตอนเจอคือ "อยู่แท็บ Failure Groups แล้วกดลูกศรนี้" ใช่ไหม ถ้าใช่ → นี่คือ UX ambiguity ไม่ใช่บั๊ก ต้องตัดสินใจในสเปกว่าจะทำยังไง: แยกปุ่มกลับสองระดับ (กลับแท็บ / กลับหน้า Import) หรือ disable ปุ่มนี้ตอนอยู่แท็บ FG แล้วให้กดที่อื่นแทน

### ② "distance of lineplot 10 min and 10 hr distance is same"

**สิ่งที่เจอในโค้ด:** `LineChart.tsx` บรรทัด ~692-693 ตั้งค่าแกน X เป็น **`type: 'category'`** ไม่ใช่ `type: 'time'`

จุดสำคัญที่ควรรู้: ECharts แกนแบบ `category` จะเว้นระยะห่างจุดข้อมูล**เท่ากันทุกจุดตามลำดับ index** ไม่สนใจว่าเวลาจริงห่างกันเท่าไร ในขณะที่แกนแบบ `time` จะเว้นระยะตามเวลาจริง — ถ้าดูข้อมูล 10 นาทีที่มี N จุด เทียบกับดูข้อมูล 10 ชั่วโมงที่มี N จุดเท่ากัน (ถูก downsample เหลือจำนวนเท่ากันทั้งคู่) ระยะห่างระหว่างจุดบนแกน X จะเท่ากันเป๊ะ เพราะมันนับ index ไม่ได้นับเวลา

**นี่ตรงกับรายงานเป๊ะ** ไม่ใช่แค่สมมติฐาน — เจอ root cause แล้วจากการอ่านโค้ดจุดเดียว

**สิ่งที่ต้องทำต่อ:** ทำซ้ำในแอปจริงเพื่อยืนยัน (ตั้งช่วง 10 นาที ดูระยะห่างจุด → ตั้งช่วง 10 ชั่วโมง ดูอีกที) แล้วเขียน spec ว่าอยากได้แกนแบบ `time` จริง ๆ ไหม — **ต้องระวัง**: การเปลี่ยนเป็น `time` axis มีผลกระทบวงกว้าง (dataZoom, tooltip formatting, tagged points ที่ผูกกับ index) จึงต้องระบุ scope ให้ dev ชัดว่าจะเปลี่ยนแค่การแสดงผลหรือกระทบ logic อื่นด้วย

### ③ "auto selected period time from data (start date and end date), not auto start date from date now"

**สิ่งที่เจอในโค้ด:** ช่อง Start/End Date เปล่า ๆ ตอนเปิด workspace ใหม่แสดงช่วงข้อมูลจริงถูกต้องอยู่แล้ว (`Dashboard.tsx` บรรทัด ~1659-1660) — **แต่** ปุ่ม "Relative range" (เช่น "ย้อนหลัง 7 วัน") คำนวณจาก **`new Date()`** คือวันนี้จริง ๆ ตามนาฬิกาเครื่อง (`Dashboard.tsx` บรรทัด ~1665) ไม่ได้อิงจากวันสุดท้ายที่มีข้อมูลจริงในไฟล์

**ผลกระทบจริง:** ถ้า CSV เป็นข้อมูลเก่า (เช่นข้อมูลของเดือนที่แล้ว) แล้วผู้ใช้กด "ย้อนหลัง 7 วัน" คาดว่าจะได้ 7 วันสุดท้ายของข้อมูล แต่จริง ๆ จะนับจากวันนี้ตามปฏิทินย้อนไป 7 วัน ซึ่งไม่ตรงกับช่วงที่มีข้อมูลอยู่เลย → กราฟว่างเปล่า

**สิ่งที่ต้องทำต่อ:** ยืนยันว่าที่ผู้ใช้เจอคือ scenario นี้ไหม (ข้อมูลเก่ากว่าปัจจุบัน) ถ้าใช่ → spec คือ "Relative range" ควรอิงจาก timestamp สุดท้ายของข้อมูล (`ts_max`) ไม่ใช่ `new Date()`

### ④ "selected between raw data and sampling data"

**สิ่งที่เจอ:** นี่คือ feature request ทับซ้อนกับ [`docs/BACKLOG.md`](BACKLOG.md) ข้อ 10 ที่บันทึกไว้แล้วว่า "Line chart plots a downsampled preview even at full raw-data resolution" — ยืนยันในโค้ดว่ากราฟ Line จำกัดที่ **4,000 จุดเสมอ** ไม่ว่าจะเลือกโหมด Raw หรือ Aggregated (`Dashboard.tsx` บรรทัด 78, ค่า `LINE_MAX_POINTS`) — ตอนนี้ไม่มีทางดูข้อมูลทุกแถวจริงได้เลยนอกจากย่อช่วงเวลาให้แคบลง

**สิ่งที่ต้องทำต่อ:** ข้อนี้ไม่ต้องทำซ้ำเพื่อยืนยันบั๊ก (มันเป็น known limitation ที่บันทึกไว้แล้ว ไม่ใช่บั๊ก) งาน BA ตรงนี้คือเขียน requirement ที่ชัดเจนว่า "ดู raw จริง" หมายความว่าอะไรในทางปฏิบัติ — เช่น ถ้าเลือกช่วงกว้างมากแล้วมีล้านแถว จะให้ทำยังไง (เตือนผู้ใช้? จำกัดช่วงอัตโนมัติ? export แยก?) เพราะโหลดล้านจุดขึ้น browser ตรง ๆ จะทำให้ค้าง — นี่คือจุดที่ต้อง trade-off ระหว่าง UX กับ performance ซึ่งเป็นงาน BA ระบุ acceptance criteria ไม่ใช่งานเทคนิคล้วน

### ⑤ "if 1 model in more than one failure group must be train model more than 1 time"

**สิ่งที่เจอในโค้ด — ซับซ้อนกว่าข้ออื่น:** โมเดล 1 ตัวมี `groupNos` เป็น array จริง (many-to-many ตามที่ตั้งใจออกแบบไว้) และถูก filter มาแสดงซ้ำในทุกกลุ่มที่มันสังกัด (`BuildModelWindow.tsx` บรรทัด ~727) — มันเป็นโมเดลตัวเดียวกันจริง ๆ ไม่ได้ถูก clone

แต่เจอ comment สำคัญใน `PredictiveModelBuild.tsx` บรรทัด ~664:
> "Fit results (relPreview / subModels / clusteringPreview) are **deliberately excluded** [จากการ persist]... **Re-opening forces the user to click Apply again**"

หมายความว่า **ทุกครั้งที่เปิดหน้า Configure ของโมเดล ไม่ว่าจะเปิดจากกลุ่มไหน ผลการเทรน/preview จะหายและต้องกด Apply/Train ใหม่เสมอ** — เป็นการตัดสินใจทาง design ที่ตั้งใจ (เพื่อไม่ให้ไฟล์ workspace ใหญ่เกิน) แต่ผลข้างเคียงคือ: ถ้าโมเดลตัวเดียวอยู่ 2 กลุ่ม แล้วผู้ใช้เปิด Configure จากกลุ่ม A เทรนเสร็จ แล้วไปเปิดจากกลุ่ม B ดูอีกที — จะเจอว่าต้องเทรนใหม่อีกรอบ ทั้งที่เป็นโมเดลเดียวกัน ตรงกับคำบ่นเป๊ะ

**สิ่งที่ต้องทำต่อ:** นี่คือข้อที่ยากสุดในกลุ่มนี้เพราะมันคือ trade-off ที่ตั้งใจทำ (เร็ว/ไฟล์เล็ก แลกกับต้อง apply ซ้ำ) ไม่ใช่บั๊กที่ไม่ตั้งใจ งาน BA ตรงนี้คือถามผู้ใช้ว่า: "การต้องกด Apply ใหม่ทุกครั้งที่เปิด เป็นปัญหาแม้จะเปิดจากกลุ่มเดียวกันก็ตามไหม หรือปัญหาคือเฉพาะตอนสลับไปมาระหว่าง 2 กลุ่มของโมเดลเดียวกัน" — คำตอบจะกำหนดว่า fix คือ "cache fit result ไว้ในหน่วยความจำระหว่างเปิด session" (เล็ก ไม่กระทบไฟล์) หรือ "เปลี่ยน design ทั้งหมดให้ persist ผล" (ใหญ่กว่ามาก)

## 4. Template สำหรับเขียน spec แต่ละข้อ

ก็อปโครงนี้ไปใช้ 1 ชุดต่อ 1 รายงาน (ทำทั้งหมด 5 ชุด):

```markdown
## [ชื่อย่อ] — [คำบ่นต้นฉบับจาก Notion]

**สถานะ:** ทำซ้ำได้ / ทำซ้ำไม่ได้ / เป็น feature request ไม่ใช่บั๊ก

**ขั้นตอนทำซ้ำ:**
1. ...
2. ...

**พฤติกรรมที่เจอ:** ...
**พฤติกรรมที่ควรจะเป็น:** ...
**เจอในเวอร์ชัน / ชุดข้อมูล:** ...

**ผลกระทบ:** ใครเจอ / บ่อยแค่ไหน / รุนแรงแค่ไหน (บล็อกงาน / น่ารำคาญ / เล็กน้อย)

**จุดที่น่าจะเกี่ยวข้องในโค้ด (ถ้าพอเดาได้):** ...

**คำถามที่ยังตอบไม่ได้ (ต้องถามผู้ใช้/dev):** ...
```

**ลำดับที่แนะนำให้ทำ:** เริ่มจาก **② (distance of lineplot)** ก่อน เพราะมี root cause ชัดเจนแล้วในโค้ด งานที่เหลือคือแค่ไปยืนยันด้วยการทำซ้ำจริงและเขียนให้ครบ template — จะเห็นภาพวิธีทำงานได้เร็วที่สุด แล้วค่อยไล่ ①③④⑤ ตามลำดับความซับซ้อน

**ส่งงานที่ไหน:** เขียนเสร็จแต่ละข้อ ส่งกลับมาให้ผู้ดูแลโปรเจกต์ตรวจก่อน แล้วค่อยเอาไปอัปเดตในการ์ด Notion ของแต่ละรายงาน (อย่าปิดการ์ดหรือเปลี่ยน Status เอง — ให้ผู้ดูแลโปรเจกต์เป็นคนตัดสินใจ)

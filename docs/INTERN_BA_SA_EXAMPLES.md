## ตัวอย่างงานที่ 2 — Glossary + สรุป business process

### Glossary entries

```markdown
## Failure Group
**นิยาม (ภาษาธุรกิจ):** กลุ่มของเซนเซอร์ที่วิศวกรรวมกันไว้เพราะสงสัยว่าเกี่ยวข้องกับ
"อาการเสีย" เดียวกันของเครื่องจักร เช่น เซนเซอร์ความดัน+อุณหภูมิ+ความสั่นสะเทือน
ของปั๊มตัวหนึ่ง ถ้าอยากดูว่าปั๊มนี้มีแนวโน้มเสียแบบไหน ก็จัดเซนเซอร์ที่เกี่ยวข้องไว้
กลุ่มเดียวกัน
**ใช้ตรงไหนในแอป:** แท็บ "Failure Groups" ในแผง Sensor ของ Dashboard —
เป็นตัวกำหนดว่าโมเดลที่เทรนไว้อยู่ในกลุ่มไหนในหน้า Build Model
**ศัพท์ที่เกี่ยวข้อง/สับสนกันได้:** "Model" — โมเดลอยู่ *ภายใน* Failure Group
(1 กลุ่มมีได้หลายโมเดล และ 1 โมเดลอยู่ได้มากกว่า 1 กลุ่ม) ไม่ใช่คนละคำแทนกันได้
```

```markdown
## Special Sensor
**นิยาม (ภาษาธุรกิจ):** เซนเซอร์ที่ "คำนวณขึ้นมาใหม่" จากเซนเซอร์อื่นที่มีอยู่แล้ว
ไม่ใช่ค่าที่เครื่องมือวัดจริง เช่น เอาความดัน 2 จุดมาลบกัน หรือคำนวณ % ประสิทธิภาพ —
ตั้งสูตรไว้ครั้งเดียว แอปคำนวณให้อัตโนมัติทุกครั้งที่มีข้อมูลใหม่เข้ามา
**ใช้ตรงไหนในแอป:** หน้าต่าง "Add Special Sensor" (แท็บ Create / Manage)
**ศัพท์ที่เกี่ยวข้อง/สับสนกันได้:** "Recipe" (สูตรคำนวณที่ผูกกับ Special Sensor
ตัวนั้น) กับ "Tag" (ชื่อที่ใช้เรียกมันในสูตรตัวอื่น เช่น พิมพ์ `$A` เพื่ออ้างถึง
sensor ชื่อ A)
```

```markdown
## Model kind: Individual / Relationship / Clustering
**นิยาม (ภาษาธุรกิจ):** 3 รูปแบบของโมเดลทำนายที่แอปนี้เทรนได้ —
Individual = ดูเซนเซอร์ตัวเดียวเทียบกับค่าปกติของตัวเอง,
Relationship = ดูว่าเซนเซอร์ตัวหนึ่งสัมพันธ์กับเซนเซอร์อื่นกี่ตัวยังไง,
Clustering = แบ่งข้อมูลเป็นกลุ่มย่อยตามช่วงค่าของเซนเซอร์อ้างอิงตัวหนึ่ง
**ใช้ตรงไหนในแอป:** ตัวเลือกโหมดในหน้า Build Model — Configure
**ศัพท์ที่เกี่ยวข้อง/สับสนกันได้:** "Target sensor" (ตัวที่อยากทำนาย ใช้ทุกโหมด)
vs "Predictor" (ตัวช่วยทำนาย เฉพาะโหมด Relationship) vs "Criteria sensor"
(ตัวใช้แบ่งกลุ่ม เฉพาะโหมด Clustering) — 3 คำนี้มักสับสนกันเพราะหน้าตาคล้ายกัน
```

### สรุป business process (ตัวอย่าง)

ไม่ต้องแยกเป็นหัวข้อย่อยแบบ glossary — เล่าเป็น flow เดียวสั้น ๆ พอ:

> วิศวกร import ไฟล์ CSV ข้อมูลเซนเซอร์จากเครื่องจักรเข้าแอป → สำรวจข้อมูลผ่านกราฟเพื่อหาความผิดปกติเบื้องต้น → ถ้าสงสัยว่าเซนเซอร์กลุ่มไหนเกี่ยวข้องกับอาการเสียแบบไหน จัดเข้า Failure Group เดียวกัน → ถ้าค่าที่มีไม่พอ อาจสร้าง Special Sensor คำนวณเพิ่ม (เช่น ค่า efficiency) → เลือกโหมดโมเดลที่เหมาะกับคำถาม แล้ว Build Model เพื่อเทรน → บันทึกผลไว้ใช้เตือนล่วงหน้าเมื่อพบสัญญาณผิดปกติในอนาคต

## ตัวอย่างงานที่ 4 — UX/Usability audit findings

```markdown
## ช่อง "Time start"/"Time end" ในหน้า Build Model ดูเหมือนเชื่อมกับ filter ของ Dashboard — หน้า Build Model (Configure)

**สิ่งที่ทำให้สับสน:** หน้า Dashboard มีช่อง filter ช่วงเวลาอยู่แล้ว แล้วพอเปิดหน้า
Build Model ก็เจอช่อง "Time start"/"Time end" หน้าตาเหมือนกันอีกชุดหนึ่ง
ไม่มีข้อความไหนบอกว่าทั้งสองชุดนี้ **ไม่เกี่ยวกันเลย** (อันหนึ่งใช้ดูกราฟ
อีกอันใช้เลือกช่วงข้อมูลสำหรับเทรนโมเดล) — เดาไปเองว่าอาจจะ sync กัน

**ทำไมถึงคิดว่าเป็นปัญหา (ผลกระทบต่อผู้ใช้):** ผู้ใช้อาจตั้งช่วงเวลาไว้ที่
Dashboard แล้วคิดว่ามันจะพกไปใช้ตอนเทรนโมเดลด้วย พอผลลัพธ์ไม่ตรงกับที่คาด
(เพราะจริง ๆ ต้องตั้งอีกรอบในหน้า Build Model) จะงงว่าทำไมผลไม่เปลี่ยน

**ข้อเสนอ (ถ้ามี):** เพิ่มข้อความสั้น ๆ ใต้หัว "Data filter" ในหน้า Build Model
ว่า "ช่วงเวลานี้ใช้เฉพาะตอนเทรนโมเดล ไม่เกี่ยวกับ filter ที่ตั้งไว้ในหน้า Dashboard"

**ความรุนแรง:** น่ารำคาญ (ไม่บล็อกงาน แต่ทำให้เข้าใจผลลัพธ์ผิด)
```

```markdown
## ปุ่มขยายกราฟเต็มจอ/ดู Sub-models เป็นไอคอนล้วน ไม่มีคำอธิบายติดปุ่ม — หน้า Build Model (กราฟ Relationship/Clustering)

**สิ่งที่ทำให้สับสน:** มุมการ์ดกราฟมีไอคอนเล็ก ๆ 2 ตัว (ลูกศรขยายมุมจอ, ไอคอน
grid สำหรับดู sub-models) ไม่มีตัวหนังสือกำกับ ต้อง hover ค้างรอ tooltip
ขึ้นก่อนถึงจะรู้ว่ากดแล้วจะเกิดอะไร

**ทำไมถึงคิดว่าเป็นปัญหา (ผลกระทบต่อผู้ใช้):** ผู้ใช้ครั้งแรกมีโอกาสไม่กดเลย
เพราะไม่รู้ว่าไอคอนนี้ทำอะไร — ฟีเจอร์ที่มีอยู่จริงเลยไม่ถูกใช้

**ข้อเสนอ (ถ้ามี):** เพิ่ม label สั้น ๆ ข้างไอคอน หรืออย่างน้อยให้ tooltip
ขึ้นเร็วกว่านี้ (ไม่ต้อง hover ค้างนาน)

**ความรุนแรง:** เล็กน้อย (ฟีเจอร์ยังใช้งานได้ แค่ discoverability ต่ำ)
```

จุดสำคัญที่ควรจับสังเกตจาก 2 ตัวอย่างนี้: finding ที่ดีจะ **ชี้ตำแหน่งชัด + อธิบายผลกระทบต่อผู้ใช้จริง** โดยไม่ต้องพูดถึงโค้ดเลยแม้แต่คำเดียว — ต่างจากการรายงานบั๊ก (งานที่ 0/1) ที่บอกว่า "ผลลัพธ์ผิดจากที่ควรเป็น" แต่ finding พวกนี้คือ "ผลลัพธ์ถูกแล้ว แต่คนงงว่าต้องทำไง"

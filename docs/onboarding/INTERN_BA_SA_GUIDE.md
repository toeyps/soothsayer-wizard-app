## 2. งานที่เหมาะกับ BA/SA ในโปรเจกต์นี้ (เรียงตามลำดับแนะนำ)

### งานที่ 0 — ทดสอบ regression ของงานที่เพิ่งทำเสร็จ (2026-09-09) ก่อนงานอื่น

**ทำไมต้องอยู่ก่อนงานที่ 1:** วันนี้มีการแก้ไข "Manage Special Sensors" และ "Build Model — Overview" หลายจุดพร้อมกัน (5 commit ในวันเดียว) ยังไม่มีใครทดสอบบนแอปจริง (ติดตั้งจาก installer) เลยสักครั้ง — commit local ไว้หมดแล้วแต่ **ยังไม่ push** เพราะรอทดสอบยืนยันก่อน นี่คืองานที่ให้ผลตอบแทนสูงสุดตอนนี้ เพราะเป็นจุดเดียวที่บล็อกการ push จริง

เปิดแอปที่ build ไว้ (หรือขอให้ dev build installer ใหม่ให้) แล้วไล่ทำตามนี้:

**A) Rename special sensor** (หน้า Add Special Sensor → แท็บ Manage → กด ✏️ ที่แถวไหนก็ได้)
1. เปลี่ยนชื่อ (field NAME) ของ special sensor ตัวหนึ่งที่ **มี** sensor อื่นสร้างต่อจากมัน (เช่นมี B = A + 1) แล้วกด Save changes — เช็คว่า B ยังคำนวณค่าถูกต้องอยู่ไหม (ไม่ใช่ค่าว่าง/error) และในกราฟที่ plot ทั้ง A(ชื่อใหม่) กับ B อยู่ ค่ายังต่อเนื่องไม่กระโดด
2. ลองเปลี่ยนชื่อเป็นชื่อที่ซ้ำกับ sensor ตัวอื่นที่มีอยู่แล้ว (ทั้งชื่อ raw sensor จาก CSV และชื่อ special sensor อื่น) — ต้องขึ้น error และกด Save ไม่ได้
3. ลองลบชื่อออกให้ว่าง — ต้องขึ้น "Name is required" และกด Save ไม่ได้
4. ปิดแอปแล้วเปิดใหม่ (หรือเปลี่ยน workspace ไปมา) — เช็คว่าชื่อใหม่ยังอยู่ ไม่กลับไปเป็นชื่อเดิม และสีเส้น/แกน Y ที่ pin ไว้/alarm line ที่เปิดไว้/Failure Group ที่ผูกไว้ ยังคงอยู่ครบตามชื่อใหม่

**B) บังคับกรอกครบ 4 ช่อง** (Name/Description/Unit/Component)
1. หน้า Create: ลองสร้าง special sensor ใหม่ กรอกแค่บางช่อง — ปุ่ม "Add sensor" ต้องกดไม่ได้ (จาง) จนกว่าจะกรอกครบทั้ง 4 ช่อง พร้อมข้อความบอกว่าขาดช่องไหน
2. หน้า Manage → เปิดแก้ไข: ลองลบ Component ให้ว่าง — ปุ่ม "Save changes" ต้องจางลงและกดไม่ได้ (ก่อนหน้านี้เคยปล่อยให้ว่างได้แล้ว fallback เป็น "Uncategorized" เงียบ ๆ — ตอนนี้ต้องพิมพ์เองแล้ว)

**C) หน้า Build Model — Overview**
1. กดปุ่ม "Group by Model Type" มุมขวาบน — ต้องเห็น section แยกตาม Individual / Relationship / Clustering (ตัวไหนไม่มีโมเดลจะไม่มี section ว่าง ๆ โผล่มา)
2. เปิดโมเดลที่ยังไม่ครบข้อมูล (เช่น Relationship ที่ยังไม่เลือก predictor) — ปุ่ม "Build Model →" ต้องอยู่ต่อจาก "Save changes" ที่มุมล่างขวาของฟอร์ม (ไม่ใช่บนหัวแถวเหมือนก่อน) และต้อง**จางลงกดไม่ได้**เหมือนปุ่ม Save changes เป๊ะ ๆ — ถ้ายังดูสีเข้มกดได้เหมือนปกติ นี่คือบั๊กที่เพิ่งแก้ไปแล้วแต่ยังไม่ยืนยันบนแอปจริง
3. กรอกข้อมูลให้ครบ แล้วลองกด "Build Model →" — ต้องพาไปหน้า train ได้ปกติ และค่าที่เพิ่งกรอกต้องถูกบันทึกไว้ด้วย (ลองกลับมาเช็คฟอร์มอีกทีว่าค่ายังอยู่)

**ถ้าพบปัญหาข้อไหน:** จดขั้นตอนทำซ้ำให้ละเอียด (ทำอะไร เห็นอะไร ควรเห็นอะไรแทน) แล้วส่งกลับมาทันที — ก่อนจะไปทำงานที่ 1 ต่อ

**สืบเนื่อง:** [`docs/testing/MANUAL_TEST_PLAN.md`](../testing/MANUAL_TEST_PLAN.md) / [`docs/testing/manual-test-plan.html`](../testing/manual-test-plan.html) เขียนไว้ก่อนงานวันนี้ ยังไม่ได้ปรับให้ตรงกับ UI ใหม่ (ช่อง Name แก้ไขได้แล้ว, มีเครื่องหมาย * ที่ทุกช่อง, ปุ่ม Build Model ย้ายตำแหน่ง, มีตัวเลือก Group by Model Type) — ถ้าทดสอบแล้วผ่านหมด งานถัดไปที่ทำได้เลยคือช่วยชี้ให้ dev รู้ว่าข้อไหนใน test plan เดิมพูดถึง UI ที่เปลี่ยนไปแล้วบ้าง

### งานที่ 1 — ทดสอบแอปทั้งระบบตาม Manual Test Plan
เปิด [`docs/testing/manual-test-plan.html`](../testing/manual-test-plan.html) ด้วยเบราว์เซอร์ (ดับเบิลคลิกเปิดได้เลย ไม่ต้องติดตั้งอะไร) ไล่ทำทีละข้อ ติ๊กผ่าน/ไม่ผ่าน จดรายละเอียดที่เจอ แล้วกด "บันทึกผลเป็นไฟล์" ส่งกลับมา

**ทำไมต้องทำก่อน:** เป็นวิธีที่เร็วที่สุดที่จะทำให้รู้จักแอปทั้งตัว เห็นทุกหน้าจอ ทุก flow — ความรู้ตรงนี้จะใช้ต่อในงานถัดไปทั้งหมด

**ข้อควรระวัง:** ต้องทดสอบบน installer ที่ติดตั้งแล้วจริง ไม่ใช่โหมด dev (`npm run tauri dev`) เพราะบางบั๊กเห็นเฉพาะในตัวติดตั้ง

**อัปเดต 2026-09-15 — งานนี้ไม่ใช่ทำครั้งเดียวจบ:** หลังจากคุ้นแอปแล้ว (ทำรอบแรกผ่านไปแล้ว) งานที่ 0/1 กลายเป็น **QA gate ประจำทุกครั้งที่จะปล่อยเวอร์ชันใหม่** ไม่ใช่แค่ทำตอนมีคนขอ — ก่อนปล่อยเวอร์ชันใหม่แต่ละรอบ ไล่ทดสอบจุดที่เปลี่ยนแปลงจริงอย่างน้อยหนึ่งรอบเสมอ และถ้าเจอว่า [`docs/testing/MANUAL_TEST_PLAN.md`](../testing/MANUAL_TEST_PLAN.md) / [`docs/testing/manual-test-plan.html`](../testing/manual-test-plan.html) ล้าสมัยไม่ตรงกับ UI ปัจจุบัน **แก้ไฟล์นั้นเองได้เลย** ไม่ต้องรอให้ dev แก้ให้ (เป็น markdown/HTML ข้อความธรรมดา ไม่ใช่โค้ดแอป) แล้วแจ้งว่าแก้อะไรไปบ้าง

### งานที่ 2 — Glossary + สรุป business process

**เป้าหมาย:** ทำให้ใครก็ตามที่ไม่รู้จักแอปนี้มาก่อน (คนใหม่, ลูกค้าในอนาคต, หรือแม้แต่ตัวน้องเองตอนเพิ่งเริ่ม) อ่านแล้วเข้าใจว่าแอปนี้ทำอะไร ใช้ศัพท์แบบไหน โดยไม่ต้องเปิดโค้ดดู

**ขั้นตอนทำงาน:**
1. เปิดแอปจริง (installer) ไล่ทำตาม flow หลักตั้งแต่ต้นจนจบ 1 รอบ: Import CSV → สำรวจข้อมูล (กราฟ) → จัดกลุ่ม Failure Group → สร้าง Special Sensor → Build Model
2. ทุกครั้งที่เจอศัพท์เฉพาะทาง (คำที่เป็นตัวหนา/เป็นชื่อปุ่ม/แท็บ ที่ไม่ใช่ภาษาไทยธรรมดา) ให้จดไว้ก่อน อย่าเดาความหมายเอง
3. ถามผู้ดูแลโปรเจกต์ว่าคำนั้นหมายถึงอะไรจริง ๆ ในเชิงธุรกิจ (ไม่ใช่เชิงเทคนิค) แล้วเขียนนิยามด้วยคำพูดของตัวเอง
4. สรุป flow การทำงานทั้งหมดเป็นข้อความสั้น ๆ 1 หน้า (ไม่ต้องมีภาพ diagram ก็ได้ ใช้ข้อความ step-by-step พอ)

**ศัพท์ที่ควรมีอย่างน้อย** (มีมากกว่านี้ได้ ถ้าเจอเพิ่ม): Workspace, Sensor / Special Sensor, Recipe/Tag, Failure Group, Model (Individual / Relationship / Clustering), Target sensor, Predictor, Criteria sensor, Data filter (Time start/end, Sensor value filter), Build Model, Save Model, Component, Description/Unit

**ทำไมต้องทำก่อนงานที่ 4:** ผลลัพธ์ของงานนี้ (นิยามศัพท์ + สรุป flow) เป็นวัตถุดิบตรงให้งานเขียน User Manual — เขียนสับสนน้อยลงถ้ามีศัพท์ที่นิยามไว้แน่นอนแล้วก่อน

**ตัวอย่าง Glossary entry + สรุป business process แบบเต็ม:** ดู [`INTERN_BA_SA_EXAMPLES.md`](INTERN_BA_SA_EXAMPLES.md)

### งานที่ 3 — Sensor/Domain Data Dictionary (ใหม่ 2026-09-15)

**เป้าหมาย:** งานที่ 2 อธิบายศัพท์ของ "แอป" (Workspace, Failure Group ฯลฯ) แต่ยังไม่มีใครอธิบายศัพท์ของ "ข้อมูล" เลย — sensor tag อย่าง `11PT1213A.PV` หรือชื่อเครื่องจักรอย่าง `GEG#4 FUEL GAS ENGINE INLET PRESSURE` มีรูปแบบการตั้งชื่อยังไง งานนี้ทำให้คนที่ไม่รู้จักระบบเซนเซอร์ของโรงงานเลย อ่าน mapping CSV แล้วพอเข้าใจได้บ้าง

**ขั้นตอนทำงาน:**
1. เปิด mapping CSV ที่ใช้จริง (ไฟล์ที่ import ตอนขั้นตอน "Prepare Dataset") ไล่ดูคอลัมน์ tag/description/unit/component
2. จดรูปแบบการตั้งชื่อ tag ที่สังเกตเห็น (เช่น ตัวย่อ PV/SP/AI คืออะไร ตัวเลข/ตัวอักษรนำหน้าหมายถึงอะไร)
3. ถามผู้ดูแลโปรเจกต์หรือวิศวกรที่ดูแลระบบจริงว่าที่สังเกตมาถูกไหม แล้วเขียนนิยามด้วยคำพูดของตัวเอง — **ห้ามเดาเอง** เพราะเข้าใจผิดแล้วกระทบความเข้าใจข้อมูลทั้งระบบ
4. รวบรวมเป็นรายการ: รูปแบบการตั้งชื่อ + ตัวอย่าง tag จริง 3-5 ตัว + คำอธิบายแต่ละตัว

**ทำไมต้องทำ:** งาน BA แท้ๆ ที่เชื่อมความรู้ธุรกิจ/วิศวกรรมกับระบบ ไม่ต้องอ่านโค้ดเลย แต่ต้องถามคนจริงเสมอ — คนละเรื่องกับ Glossary งานที่ 2 ที่อธิบายแค่ UI ของแอป

**Template:** ใช้โครงเดียวกับ Glossary entry ในหัวข้อ 3 ได้เลย แค่เปลี่ยนหัวข้อจาก `[ศัพท์]` เป็น `[รูปแบบ/ตัวอย่าง tag]`

### งานที่ 5 — UX/Usability audit

**เป้าหมาย:** หา "จุดเสียดทาน" ที่ทำให้ผู้ใช้จริงสับสน/ใช้งานผิด/ต้องเดา — **ไม่ใช่การหาบั๊ก** (บั๊กคือแอปทำงานผิดจากที่ออกแบบไว้ ส่วนงานนี้คือแอปทำงาน "ถูก" แล้ว แต่ผู้ใช้ยังงงว่าต้องทำยังไง)

**ต่างจากงานที่ 1 ยังไง:** งานที่ 1 มีคนเขียนขั้นตอนไว้ให้แล้วทุกข้อ (ทำตามได้เลย ไม่ต้องคิด) ส่วนงานนี้ให้น้องเดินเข้าไปแบบ "ไม่มีใครบอกขั้นตอน" เหมือนผู้ใช้จริงคนแรกที่เปิดแอปโดยไม่มีคู่มือ

**ขั้นตอนทำงาน:**
1. เปิดแอปจริง สมมติว่าตัวเองเป็นคนใหม่ที่ไม่เคยเห็นแอปนี้มาก่อน (ลืมทุกอย่างที่รู้จากงานที่ 0/1 ไปก่อน)
2. ลองทำงานหลัก 1 อย่างให้จบ (เช่น "import CSV แล้วสร้างกราฟดูเซนเซอร์ตัวหนึ่ง") โดยไม่เปิดคู่มือ/ไม่ถามใคร
3. ทุกครั้งที่ต้อง**หยุดคิด/เดา/อ่านซ้ำ** ให้จดตรงนั้นทันที (อย่ารอจดตอนจบ จะลืม) — สังเกต 3 อย่างนี้โดยเฉพาะ:
   - **คำศัพท์ไม่สอดคล้องกัน**: ปุ่ม/label/ชื่อแท็บ เรียกสิ่งเดียวกันไม่เหมือนกันในหน้าต่างกัน
   - **flow สับสน**: ต้องเดาว่าต้องกดอะไรก่อน/หลัง ไม่มีการชี้นำ
   - **ข้อความไม่ช่วยอะไร**: error message หรือ hint text ที่อ่านแล้วยังไม่รู้ว่าต้องแก้ยังไงต่อ
4. เขียนแต่ละจุดที่เจอเป็น finding ตาม template ด้านล่าง

**ตัวอย่าง finding ที่เป็นไปได้** (สมมติ ไม่ใช่ของจริง แค่ให้เห็นภาพระดับความละเอียดที่ต้องการ): "หน้า Build Model มีตัวเลือก Individual/Relationship/Clustering แต่ไม่มีคำอธิบายสั้น ๆ ว่าแต่ละแบบต่างกันยังไง ต้องเดาจากชื่อเอาเอง" — นี่คือ UX finding ที่ดี เพราะชี้จุดสับสนจริง ไม่ต้องรู้โค้ดเลยก็สังเกตได้

### งานที่ 6 — Release Notes ฉบับผู้ใช้จริง (ใหม่ 2026-09-15)

**เป้าหมาย:** [`docs/release/CHANGELOG.md`](../release/CHANGELOG.md) เขียนแบบกึ่งเทคนิคโดย dev สำหรับคนที่ทำงานต่อบนโค้ด — งานนี้คือเขียนสรุป "เวอร์ชันนี้มีอะไรใหม่/แก้อะไรบ้าง" แบบสั้นๆ ภาษาคนใช้งานจริง (ไม่ใช่ dev) แนบไปกับทุกครั้งที่ปล่อยเวอร์ชันใช้งานจริง

**ขั้นตอนทำงาน:**
1. อ่าน `docs/release/CHANGELOG.md` ของเวอร์ชันที่กำลังจะปล่อย (เขียนไว้แล้วโดย dev)
2. แปลเป็นภาษาคนใช้งาน 3-5 บรรทัด: เน้น "จะเห็นอะไรเปลี่ยนไปตอนเปิดแอป" ไม่ใช่ชื่อฟังก์ชัน/ไฟล์ที่แก้
3. ส่งให้ผู้ดูแลโปรเจกต์ตรวจก่อนแนบไปกับตัวติดตั้งจริง

**ทำไมต้องทำ:** เติมช่องว่างที่น้องฝึกงานไม่เคยมีส่วนร่วมในขั้น "ใช้งานจริง" เลยมาก่อน — ตอนนี้มีบทบาทครบทุกขั้นตอนของกระบวนการทำงานจริง

### งานที่ 7 — เขียน Test Case ล่วงหน้าให้ฟีเจอร์ใหม่ (ใหม่ 2026-09-15 — ทำเมื่อคล่องกับแอปแล้ว)

**เป้าหมาย:** เปลี่ยนจาก "ทดสอบของที่ทำเสร็จแล้ว" (reactive, งานที่ 0/1) เป็น "เตรียมขั้นตอนทดสอบไว้ล่วงหน้า" — พอมี feature ใหม่ที่**ตัดสินใจจะทำแล้ว** (ผู้ดูแลโปรเจกต์อธิบายให้ฟัง) น้องเขียนขั้นตอนทดสอบ/acceptance criteria ไว้ล่วงหน้า ก่อน dev เริ่มทำด้วยซ้ำ

**ไม่ใช่ Requirement gathering:** งานนี้ไม่ใช่ไปเก็บ requirement จากใคร (แอปนี้ไม่มี external user ให้เก็บอยู่แล้ว ดูหมายเหตุด้านล่าง) แต่เป็นการ**แปลง feature ที่ตัดสินใจแล้ว**ให้เป็นขั้นตอนตรวจสอบว่า "ทำเสร็จแล้วรู้ได้ยังไงว่าใช้งานได้จริง" — เหมือนงานที่ 0/1 แค่ทำก่อนแทนที่จะทำหลัง

**ขั้นตอนทำงาน:**
1. ฟังคำอธิบาย feature ใหม่จากผู้ดูแลโปรเจกต์ (สิ่งที่อยากได้ ไม่ใช่วิธีทำ)
2. เขียนเป็นรายการ "ทำ X แล้วควรเห็น Y" ให้ครอบคลุมทั้งกรณีปกติและกรณีขอบ (เช่น กรอกไม่ครบ, กดซ้ำ)
3. ส่งให้ผู้ดูแลโปรเจกต์ตรวจก่อนส่งต่อให้ dev เริ่มทำ
4. พอ feature เสร็จ ใช้รายการเดียวกันนี้ไล่ทดสอบจริง (วนกลับไปรูปแบบงานที่ 0)

**Template:** ใช้โครงเดียวกับงานที่ 0/1 (รายงานปัญหาที่พบ) กลับด้าน — เขียน "ขั้นตอนทำซ้ำ" + "พฤติกรรมที่ควรจะเป็น" ไว้ล่วงหน้า โดยยังไม่มี "พฤติกรรมที่เจอ" (เติมทีหลังตอนไล่ทดสอบจริง)

> **หมายเหตุ:** การวิเคราะห์รายงานที่ค้างใน Notion, การแปล backlog เป็น user story, และการเก็บ requirement จาก stakeholder ภายนอก ผู้ดูแลโปรเจกต์ทำเองอยู่แล้ว (แอปนี้ใช้ภายในเท่านั้น ยังไม่มี external user ให้ไปเก็บ requirement จากใครอื่น) — ไม่ต้องมอบหมายให้น้องฝึกงาน งานที่ 7 ด้านบนแม้จะฟังดูใกล้เคียงก็เป็นคนละเรื่องกัน (แปลง feature ที่ตัดสินใจแล้ว ไม่ใช่ไปเก็บ requirement เอง)
